# Netgap Roadmap

Where the scanner is useful today, and what would make it more so. Ordered by
value against effort, not by how interesting the work is.

Two questions drive everything here:

1. **Security** — is anything on this network actually wrong?
2. **For normal users** — what *are* these devices, in words a non-technical
   person can act on?

The tool answers "who is connected" well now. It does not yet answer "is
anything wrong", and its device descriptions are thinner than they look.

---

## Near term

### 1. Real OUI vendor database — ✅ done

Replaced the hand-written 20-entry table with the full IEEE registry
(54,104 assignments across MA-L, MA-M and MA-S), generated by
`tools/update-oui.py` and bundled so lookups need no network.

On a real network this turned a column of dashes into `Intel Corporate`,
`Apple`, `Ruijie Networks`, `AzureWave Technology`. Vendor names now also feed
device classification, so `Intel Corporate` reads as "Computer".

Still open: names for the devices that randomize their MAC, which no OUI
database can supply. That is what mDNS is for (next).

### 2. Implement mDNS discovery — ✅ done

`netgap-mdns` browsed nothing and returned an empty `Vec`; it now browses ~21
service types with `mdns-sd`, converts resolved records into `MdnsService`, and
merges them into the device list: naming hosts, filling in device types, and
adding hosts only mDNS knew about.

This is the biggest "what is this device?" win for a normal user, because
devices name *themselves*: `HP LaserJet MFP`, `Chromecast`, `Sonos Play:5`
instead of "Unknown device" and a randomized MAC. It also covers exactly the
devices OUI lookup cannot reach.

**Caveat: not yet observed working on a real network.** The development machine
does not deliver multicast back to its own sockets — verified with a bare socket
pair, no library involved — so a service announced locally is never seen by a
browser on the same host. That makes the loopback integration test (`#[ignore]`d
in `netgap-mdns`) unable to pass there, and left the browse path validated only
by unit tests over real `ServiceInfo` values. It needs a run on a network where
mDNS actually flows; the same networks where AirPlay and Chromecast discovery
work in a browser is the practical test.

That also means the "no mDNS services answered" message is currently the honest
output on this network — worth checking whether the AP filters multicast between
clients, since that breaks other discovery protocols too.

### 3. Service and version detection, then real CVE data — partially done

**Probes: done.** `--fingerprint` now goes through `netgap-probes` instead of
re-implementing banner grabbing inline for four ports. The crate separates
*product* from *version* (`nginx` `1.18.0`, not "HTTP/1.1"), covers HTTP, HTTPS,
SSH, FTP, Telnet, SMTP, IMAP, POP3, VNC, MySQL/MariaDB, PostgreSQL, Redis and a
generic TCP fallback, and dispatches by port. Verified end to end against a
real server: `Server: Apache/2.4.49` produced exactly the two CVEs that affect
2.4.49, and nothing else.

Three correctness problems surfaced while wiring it and are fixed:

- **Version comparison was a string compare.** `"2.4.9" < "2.4.10"` is false as
  text, so a vulnerable host was reported clean. Comparison is now numeric,
  component by component.
- **Ranges could only be one-sided.** `< X` cannot express a real CVE window,
  so the format now accepts `>= 2.4.49, < 2.4.51`.
- **One entry was fabricated.** CVE-2021-44228 is Log4Shell — a Log4j issue
  with no httpd version range — and was listed as affecting Apache `< 2.4.50`.
  Replaced with CVE-2021-42013, which is the httpd flaw in that window.

**NVD client: done.** `netgap-threat-intel` now queries the real API instead of
returning three hardcoded entries, two of which had fabricated identifiers
("CVE-2023-01234"). Three commands and one flag:

```
netgap threat-intel update     # fetch by product into the local cache
netgap threat-intel status     # what the cache holds
netgap scan --threat-intel     # match findings against the cache, offline
netgap scan --threat-intel --threat-intel-update   # fetch for services found
```

Two design points that came out of testing against the live API:

- **Lookups are per version, not per product.** `fetch_product` returns every
  CVE ever filed against a product, oldest first, with no sort parameter
  available — for Apache that is 351 entries starting in 1999, and a limit
  truncates to the *oldest*. Querying `cpeName=...:http_server:2.4.49` instead
  makes NVD apply its own version-window matching server-side and returns the
  81 entries that actually apply. The bulk path now sorts newest-first and says
  why it is second choice.
- **The cache records which versions it was populated for.** It holds what was
  asked for, not a mirror of NVD, so matching a version that was never queried
  would silently under-report. `queried_versions` makes that detectable, and
  scan-driven updates fetch only the versions not yet covered.

Verified against a live server reporting `Server: Apache/2.4.49`: the probe read
the banner, the CPE mapping resolved `apache:http_server`, and NVD returned 81
CVEs whose top entries are the genuine 2.4.49 flaws — CVE-2021-41773,
CVE-2021-42013, CVE-2021-44790, CVE-2022-22720.

**Still to do:**

- The bundled six-entry database in `netgap-services` remains as a fallback for
  when no NVD cache exists; several of its ranges should be checked against NVD
  (CVE-2021-26691's fixed version in particular).
- **Bulk coverage.** The per-version API only populates the cache for versions a
  scan has seen. Covering a product wholesale means many date-windowed requests
  (the API caps `pubStartDate`/`pubEndDate` at 120 days and has no descending
  sort). The right answer is the NVD bulk feeds, which need gzip and streaming
  JSON parsing.
**TLS inspection: done.** `probe_https` reads the `ServerHello` and
`Certificate` messages directly instead of completing a handshake, because the
devices most worth inspecting are the ones a real handshake cannot reach: the
gateway on the development network offers only static-RSA cipher suites, which
rustls refuses outright. Reading two messages needs no key exchange, so the
certificate arrives regardless.

It reports the negotiated version, the cipher suite, whether the server still
accepts a TLS 1.0 hello, and the leaf certificate's subject, issuer, validity
and whether it is self-signed. Findings: legacy TLS accepted (High), static RSA
without forward secrecy (Medium), expired certificate (High), expiring within
30 days (Medium), self-signed (Info — normal on a LAN, so reported without
alarm).

Certificate fields are read with a small DER reader rather than an X.509 crate,
which would have pulled in a parser stack for four fields.

Verified against two live servers: the gateway (TLS 1.2, static RSA, self-signed,
reported correctly) and an `openssl s_server -tls1` instance, which was detected
as `TLSv1.0` and flagged. That second test found a real bug — the SNI extension
was missing the list-length prefix RFC 6066 requires, which the router tolerated
and OpenSSL rejected.

**Still open on this item:**

- The bundled six-entry database in `netgap-services` remains as a fallback for
  when no NVD cache exists; several of its ranges should be checked against NVD
  (CVE-2021-26691's fixed version in particular).
- **Bulk coverage.** The per-version API only populates the cache for versions a
  scan has seen. Covering a product wholesale means many date-windowed requests
  (the API caps `pubStartDate`/`pubEndDate` at 120 days and has no descending
  sort). The right answer is the NVD bulk feeds, which need gzip and streaming
  JSON parsing.

### 4. "New since your last scan" — ✅ done

Devices are now tracked across scans in a `device_seen` table keyed by MAC (or
by address when no MAC is known), holding first sighting, last sighting and how
many scans have included them. The discovery report gained a `Seen` column and
a count of what is new:

```
  Devices connected: 20    Trusted: 3    Unrecognized: 17
  Seen for the first time: 2

  IP             Name            MAC                Type              Seen   Status
  192.168.111.1  gateway/router  C4:B2:5B:0A:03:26  Router / gateway  now    trusted
  192.168.111.56 —               D2:07:6E:B6:B2:CA  Phone / laptop    3h     UNRECOGNIZED
  192.168.111.71 —               A2:2D:98:D1:F6:8F  Phone / laptop    new    UNRECOGNIZED
```

`discover` records what it saw, so the next run can compare; `--no-save` opts
out. A device first seen *before* the previous scan keeps its original
timestamp, so "new" means genuinely new rather than merely absent last time.

One caveat worth knowing: a device that randomizes its MAC changes identity
between scans and will look new again. The history is honest about what it
observed, not clairvoyant about what a device is.

## Security

### 5. TLS and router-admin checks — ✅ done

**TLS** is inspected: negotiated version, cipher suite, certificate subject,
issuer, validity and self-signed status, plus whether the server still accepts
a TLS 1.0 hello. Findings for legacy TLS (High), static RSA without forward
secrecy (Medium), expired (High) and expiring (Medium) certificates, and
self-signed certificates (Info).

**Gateway checks** run against one host, identified exactly because it owns the
default route. The port scan does not cover router-specific interfaces, so the
gateway gets a focused pass over its administration and UPnP ports:

```
Gateway checks (192.168.111.1)
  Administration page: HTTP/1.0 200 OK
  [MEDIUM] Gateway administration is reachable over plain HTTP
```

It reports an administration interface served over plain HTTP *in addition* to
HTTPS — the case the general check cannot see, since that one stays quiet when
HTTPS is available — and an exposed UPnP control interface, which lets any
device on the network open inbound ports without authentication.

Known limits, in the code as well as here: the UPnP check reads TCP ports only.
Discovery runs over UDP 1900, which is not probed, so a router exposing SSDP
without an HTTP control interface is missed rather than misreported. Nothing
here tests credentials — whether a default password still works cannot be
determined from a port, and guessing at it would produce exactly the kind of
confident wrong answer this codebase has been removing.

### 6. Watch mode should look for attacks, not just drift — partly done

`watch` re-scanned on a timer and diffed the results, which an attack between
two scans stays invisible to. It now also watches for an address changing
hands, in whichever way the scan is able to see it.

**Unprivileged (the usual case).** Each cycle snapshots the kernel's neighbour
table for the interface being watched and compares it to the previous cycle. A
device that took an address over and is still using it shows up there, because
ordinary traffic keeps the table current. No capture, no privileges.

**Privileged.** A raw-socket ARP sweep sees every reply, so an address answered
by two different hardware addresses *within one sweep* is caught immediately,
before anything has settled. Only this path can see it: the kernel keeps one
entry per address, so a table read cannot show two devices claiming one.

What an alert says depends on which address moved. The gateway is the one worth
impersonating — everything leaving the network passes through it — so a change
there reads as an alert with both addresses named, while a change on a printer
is reported plainly. One device answering for several addresses is only raised
when one of them is the gateway, since a machine holding two of its own
addresses is ordinary.

Nothing is called an attack. A changed mapping has innocent explanations — a
replaced device, a laptop bridging Wi-Fi and Ethernet, a phone that randomized
its address and reconnected — so the finding states what was seen and lets the
owner judge it.

**Rogue DHCP: done.** A DHCP server tells every device which gateway and DNS
server to use, so a second one on a network can quietly redirect what those
devices send. `watch --check-dhcp` sends a DHCP DISCOVER and collects whoever
answers, reporting any server that is not the gateway:

```
  DHCP server: 192.168.111.1 (router)
🚨 ALERT: an unexpected DHCP server answered — 192.168.111.99 (not-the-router)
```

The check is active rather than passive on purpose: a listener only sees
traffic when something else triggers it, which on a quiet network can be
nothing for hours, whereas asking gets an answer now. The cost is a side
effect worth stating — a server will hold the offered address briefly, as it
would for any device joining — so the probe reuses one client identity rather
than looking like a new device each time.

It needs root: a DHCP client binds port 68, below 1024, and sends to the
broadcast address. There is no unprivileged way to do it, and the flag says so
rather than failing quietly. If this machine is itself a DHCP client, port 68
may already be held, which the error message explains.

**Replies are read from a raw packet socket, not the UDP socket.** The first
version listened on the client socket and found nothing against a real
network, while the machine plainly held a DHCP lease from that same router.
Measuring the path directly showed why: a broadcast sent to a local interface
never reaches a UDP listener on this host, with or without the tool involved.
A host firewall dropping inbound broadcast is the likely cause, since a
locally-originated broadcast still travels through the input path.

Packet sockets are tapped before netfilter, which is exactly why real DHCP
clients read this way — and why a machine can hold a lease while a plain UDP
listener sees nothing. The capture is opened before the DISCOVER is sent, so a
server answering within milliseconds is not missed. The UDP path remains as a
fallback for a machine that has `CAP_NET_BIND_SERVICE` but not `CAP_NET_RAW`.

**Known limits.** This observes what has settled rather than listening
continuously, so a spoof that starts and stops between two cycles is missed;
closing that needs a privileged capture loop, which is the honest next step.
The DHCP check expects the gateway to be the server, which is right for a home
network and wrong for one with a dedicated server — when no expectation is
known it reports the server as information rather than as an alert.

**Verifying the DHCP check.** It cannot run unprivileged, and the development
machine has no capabilities, so it is covered end to end only against a
stand-in server on a high port. To check it for real, with nothing touching the
live network:

```
sudo ip link add netgap-test type dummy
sudo ip addr add 10.99.99.1/24 dev netgap-test
sudo ip link set netgap-test up
sudo dnsmasq --interface=netgap-test --bind-interfaces \
     --dhcp-range=10.99.99.50,10.99.99.100,12h --port=0 --no-daemon &

sudo ./target/release/netgap watch -y --check-dhcp \
     --interface netgap-test --target 10.99.99.0/24

sudo pkill dnsmasq && sudo ip link del netgap-test
```

A server at 10.99.99.1 is not the gateway, so it should be reported as
unexpected. Against the real network, `--check-dhcp` should name the router and
raise nothing — unless something else is answering, which is the finding.

**This recipe has not worked yet, and the reason is instructive.** On the
machine it was tried, a broadcast sent to a local interface never reaches
another socket on the same host: unicast does, broadcast and multicast do not.
That was measured directly, with and without the tool in the path, and it also
explains why mDNS found nothing. A host firewall (firewalld is running here)
dropping inbound broadcast is the likely cause, since a locally-originated
broadcast is still delivered through the input path.

It matters only for the same-host rig. On a real network the DHCP server is a
different machine, which receives the request normally; only the *reply* comes
back through this host's input path. So the check is more likely to work
against a real router than in this loopback recipe, and the honest thing to do
first is run it against the real network.

If the loopback recipe is wanted anyway, the interface has to be exempt from
the firewall:

```
sudo firewall-cmd --zone=trusted --change-interface=netgap-test
```

The no-answer message now says a firewall may be hiding a server rather than
suggesting only that the network uses static addressing.

### 7. IPv6 — ✅ discovery done, port scanning not

`Ipv4Addr` was used throughout discovery, so on a dual-stack network every
IPv6-only device was invisible and any device count was quietly wrong.

**IPv6 has no ARP, and a `/64` cannot be swept** — 2^64 addresses is not a list
anyone walks. What works is the kernel's neighbour table, which is IPv6's
equivalent of the ARP cache. Discovery is two steps: send an ICMPv6 echo to the
all-nodes multicast address (`ff02::1`), which every IPv6 host on the link
receives, then read the table back through netlink — the same source
`ip -6 neigh` reads.

**This runs unprivileged**, unlike the ARP path. The echo goes through a
datagram ICMPv6 socket, which the kernel builds and checksums and which
`net.ipv4.ping_group_range` opens to ordinary users, and netlink needs no
capability at all. So IPv6 discovery runs on every scan, not only under sudo.

Addresses are attached to devices by hardware address — the one identifier both
sides of the split agree on, and one that survives MAC randomization because the
same random address appears on both. A neighbour matching no known device
becomes one, but only when the scan covered the whole link: the table covers
every host regardless of `--target`, and honouring it unfiltered would report
devices the user asked not to scan.

Verified against the live network: the reader returns exactly what
`ip -6 neigh` returns, 12 neighbours, and the addresses correlate with the IPv4
devices the way EUI-64 says they should — MAC `C4:B2:5B:0A:03:26` and
`fe80::c6b2:5bff:fe0a:326`, which is that MAC with the universal/local bit
flipped. The stimulator earns its place too: it found a host that was not in the
table before the run.

That live check also caught a bug the unit tests could not: the table holds an
entry for every multicast group the machine has joined — `ff02::1`, `ff02::fb`,
and so on — each with a synthetic `33:33:` MAC. Merging those would have
invented six devices on every scan.

**What is still IPv4-only:**

- **Port scanning a link-local IPv6 device.** A `fe80::` address is only
  reachable with a zone (the interface) attached, which a `Device` does not
  record, so such devices are skipped with a note rather than probed. Reporting
  them as "no open ports" would be a different claim from "not scanned".
- Everything IPv4-specific downstream: gateway checks, DHCP, ARP conflict
  detection. IPv6 devices are discovered and reported; they are not yet
  assessed.

### 8. Continuous integration and `cargo audit` — ✅ done

Four gates on every push and pull request, in `.github/workflows/ci.yml`:
`cargo test --workspace --locked`, `cargo fmt --check`,
`cargo clippy --all-targets -- -D warnings`, and `cargo audit`. The audit also
runs on a weekly timer, because advisories are published against code that has
not changed — a green run last month says nothing about today.

`--locked` throughout, so CI builds the dependencies the lockfile pins rather
than resolving new ones underneath it.

**A green local run is not evidence.** The first push failed on clippy while
passing here: CI's stable is 1.98 and this machine's default is 1.89, and
clippy gained three lints in between, one per crate, each revealed only after
the previous was fixed. The workflow then caught the same class of problem in
reverse, so the CI toolchain is now installed alongside the default —
`cargo +1.98.1 clippy --workspace --all-targets -- -D warnings` is the check
that predicts CI. A `rust-toolchain.toml` pinning the version would remove the
guesswork entirely; it is not here because it silently downloads a toolchain
for anyone who runs cargo in this repository.

**The first audit found four real vulnerabilities**, all from one dependency:
`reqwest 0.11` sits on the hyper 0.14 and rustls 0.21 line, which carry an
unbounded-memory denial of service in `h2` and three certificate-validation
flaws in `rustls-webpki` — two of them accepting certificates that should have
been rejected. No update within those majors fixes them, so both crates that
use reqwest now ask for 0.12, which moved to hyper 1.x and rustls 0.23. The
source needed no changes: the whole API surface used here is `Client`,
`.header()`, `.send()`, `.status()` and `.text()`. The live NVD query was run
again afterwards to confirm the client still talks to the real API.

Three unused dependencies were carrying advisory weight of their own:
`ratatui` (in the CLI and the report crate) and `indicatif` (in three crates)
were declared but never referenced — no source file mentions either. The
interactive view draws with `crossterm` directly. Removing them dropped ten
packages from the lockfile and took `lru`'s two unsoundness advisories and
`paste` with them; `anyhow` and `spin` were updated to their fixed versions.
`cargo audit` now reports no vulnerabilities and no warnings across 260
dependencies.

Two things were needed before the lints gate could pass at all. The workspace
had never been formatted — 27 files, 1,114 lines — so that is its own commit,
easy to skip in `git blame`. And `netgap-raw-sockets` had six lint errors; the
fixes are in that commit too, including one that matters: `scan_ip` returned
`Ok(None)`, which reads as "no device answered" from a crate that sends
nothing. It now returns an error saying it is unimplemented.

**Not done, and worth knowing:** the actions are pinned to major-version tags
rather than commit SHAs, so a compromised or retagged action would run. That is
the usual trade against having to hand-update SHAs, but for a tool whose whole
purpose is supply-chain visibility it is the weaker choice, and pinning is a
contained change if wanted.

## For normal users

### 9. A plain-language risk summary in `scan` — ✅ done

Every scan report now opens with the conclusion instead of the detail:

```
  38/100 — several problems need attention

  What matters most:

    🟠 2 databases are reachable on the network
      on 192.168.111.70, 192.168.111.187
      It usually holds everything the network's applications know, and is
      often set up to trust whoever connects.
      → Restrict it to the machines that need them, and set a password.

    🟠 File sharing (SMB) is switched on for 2 computers
      on 192.168.111.96, 192.168.111.187
      It is how ransomware spreads from one computer to the next on a home
      network.
      → Turn file sharing off on the computers that do not need it, and
      password-protect the folders that are shared on purpose.
```

Findings are grouped by *kind* rather than by port: one Windows machine with
both SMB ports open is one problem, not two, and the same problem on three
machines is one sentence with a count in it. `IssueKind` in `netgap-core` does
the classification, keyed on the finding identifier with the port as a
fallback; the wording and the advice live in `netgap-report`.

**Scoring was measuring the wrong thing.** The old `HealthScore` subtracted a
point per device and per open port, so a large healthy network scored worse
than a small compromised one: this nineteen-device network with one computer
sharing files scored 52 ("Fair"), because 47 of the 48 points lost were for
being large. The score now comes from the problems found, charged once per
kind at its worst severity, plus a smaller amount for each further device —
repetition is a weaker signal than the first occurrence, so the fourth laptop
sharing files is not four times the problem. It lives in `netgap-core`, which
lets `watch` and the report share one formula; both now say 38/100 for the
same network.

**A verdict must not overclaim in either direction.** A high score reads
"looks healthy", never "no problems found" — a scan can score 88 and still
list something three lines below. The opposite case is handled by wording:
a port that accepts connections is reported as *reachable*, not as "answering
to anyone who asks", because reachability is what was measured. A scan that
finds nothing says so, then says what it did not check.

**The summary was only as good as the findings under it.** On the first real
run it said "looks healthy" about a network with Remote Desktop open, because
the port scanner only produced findings for three ports (Telnet, SMB,
NetBIOS). It now has a small table of ports that are worth a finding on their
own — RDP, VNC, databases, the r-services — each with its own explanation and
fix. That immediately surfaced two machines answering on 3306 and one on 3389,
none of which the tool had ever reported. Every one was confirmed by hand from
outside the tool before the claim was believed; `netgap scan` had been finding
these ports all along and simply saying nothing about them.

**Still open:** the summary appears in the terminal and `--format summary`
output, but not in JSON or the markdown/HTML exports. The advice is per kind,
not per device — it cannot yet say "turn it off on the printer but not on the
NAS". And `--assess` remains a separate flag: a scan without it reports
exposure, but not vulnerabilities.

### 10. Shareable HTML discovery report — ✅ done

```
netgap discover --format html --output network.html
```

One self-contained file: no scripts, no stylesheets fetched, no fonts — it
opens from a file:// path on a machine that has never been online, which is
what makes it something you can email to a landlord or keep in a folder. It
carries what the terminal report has (counts, trust state, IPv6 addresses)
plus the full device table with no column truncation, and it collapses to one
column on a phone with a print stylesheet for paper.

`--output` was added alongside it because "keep a dated snapshot" is the point:
without it the only way to save a report was to redirect stdout.

**The escaping is the part that matters.** Every string in a report is chosen
by a device or a person: hostnames from reverse DNS, mDNS names a device
advertises, service banners, TLS certificate subjects, and labels a user typed.
Interpolated raw into HTML, a device can put a `<script>` tag in a page that
someone opens later — the report about a hostile device becomes the hostile
thing, and the reader is the target. `netgap_core::html::escape` now covers
`& < > " '`, and both HTML writers use it.

That second writer is the older scan export, which had **no escaping at all** —
finding titles and descriptions arrive from banner text, so a device answering
with `<img src=x onerror=...>` in its `Server:` header was writing script into
the report of every scan that found it. Fixed here, with a test that pushes a
hostile hostname, title and description through a real database and asserts
none of them survive as markup.

Two smaller things the work turned up: writing the colourised terminal report
to a file embedded ANSI escape codes in it, because `colored` decides by
looking at stdout, which is still a terminal when the destination is a file;
and JSON output said "open it in a browser". Both fixed.

**Still open:** the scan HTML export keeps its own older styling and was not
converted to the shared one, so the two reports look different. A test asserts
the discovery document fetches nothing from the network; the scan export has
no equivalent guard.

### 11. Alerts that reach the user

`netgap-webhooks` (alert delivery, 6 tests) and the `AlertRule` types are both
unreachable from the CLI — alerts only print inside `watch`. Firing them on a
critical finding from `scan`, and on a schedule via a systemd timer or cron, is
what makes this a monitor rather than something you remember to run.

## Deliberate non-goals

- **No "unauthorized device" verdicts.** The tool cannot know who is welcome on
  a network, and an unrecognized MAC is exactly what the owner's own phone with
  a randomized address looks like. Devices are reported as `trusted` or
  `UNRECOGNIZED`, and the judgement stays with the user.
- **No exploit execution.** Version and configuration checks only — no attempt
  to exploit a finding.
- **No cloud dependency.** Scanning a home network should not require an
  account or a network round trip.
